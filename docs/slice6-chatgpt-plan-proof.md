## 2. The three documentation gaps

**Eligibility for this private Android app: not resolved by public text.**
- Plan usage is offered to "open-source projects, personal projects that run locally, and selected private apps". Paid or remotely hosted apps join a waitlist.
- Thalia is a private, personal, on-device app with no server and no charge. "Personal project that runs locally" is the closest category, but the pages never define it, never mention Android or closed-source apps, and nothing says the source must be public.
- **The repository stays private.** The honest ways to settle it are the proof itself (dynamic registration is self-serve in the documented flow; if it works, that is evidence, not authorization, and OpenAI can change or withdraw it) and, if reliance beyond the proof is wanted, asking OpenAI through the interest form or support. I have not contacted OpenAI and will not.

**Applicable terms: only second-hand.** The Sign in with ChatGPT Terms, the Service terms and the help articles returned HTTP 403 to my fetches, so I could not read them. Search summaries of the Sign in with ChatGPT Terms say: requests must come from the user's own runtime; the user's plan may serve only the application they connected; persistent token storage must be local and under the user's control; no asking for ChatGPT passwords or session cookies; express consent before any background use; plan usage grants no extra usage or access. Thalia's design meets each of these, but **you should read the terms yourself before signing in**: openai.com/policies/sign-in-with-chatgpt-terms.

**Can paid credit spending be prevented before a request: no verified control exists.**
- Read directly on the official pages (2026-10-10): no request header or parameter selects or forbids a billing path; the errors page says "OpenAI does not silently switch the request to another billing path"; the profiles-and-sessions page says ChatGPT Settings, Usage lets the user "manage each app's access to their ChatGPT plan and credits" and set limits per app. Nothing there says credits are off by default, and **no page I could read mentions a weekly cap or "100%"**. The earlier claim that credits "need the cap set to 100%" came from a secondary source and is **unverified**; it is no longer presented as a control.
- The only possible control is the user's per-app setting in ChatGPT, which exists only after the app has signed in once, and which the app cannot read. Comparing balances afterwards detects spending; it does not prevent it.
- What the proof now does: sign-in sends no model request. Every request path (model list, reply check, fixtures) is refused until the owner ticks a box, enabled only when signed in, saying they checked Usage and this app has no credits access. The box clears on sign-out. This is an **attestation by the owner, not enforcement**, and the screen says so.
- Residual risk, kept open: if the setting does not mean what its label says, or the default grants credits access and the screen is misread, a request could draw credits. Mitigations are the 14-request ceiling, a before-and-after balance check, and stopping on any movement. Whether a limit of 0 or "plan only" can be set per app is a question for the Usage screen itself.

## 3. What the proof contains

Build type `chatgptCheck` (application id `com.thalia.app.chatgptcheck`) and module `:chatgpt-plan`. Own data directory, Keystore alias and planning names. It reads and writes nothing of `com.thalia.app.debug`, `geminicheck`, `conversationcheck` or `recoverycheck`. `INTERNET` is requested only by this build type, `geminiCheck` and the debug M3A spike; release has none (checked in the merged manifests).

- **Sign-in** (`SignInFlow`): loopback listener on 127.0.0.1 only, started before the browser; the callback's state is checked; wrong-state and other-path requests are ignored; the code is exchanged with the same redirect URI; the ID token's **RS256 signature is verified** against the JWKS found through `https://auth.openai.com/.well-known/openid-configuration` (`jwks_uri` must stay on that host; unknown `kid` refetches once; `alg` other than RS256 refused), then issuer, audience, expiry, issued-at, subject and nonce are checked; the plan scope is required; credentials are written sealed and atomically.
- **Renewal** (`PlanSession`): one renewal at a time, because a rotated refresh token cannot be spent twice; the new pair is saved before use; a failed save keeps the pair in memory; a rejected refresh signs out locally; an outage keeps the sign-in. The refresh request sends only the documented fields (`grant_type`, `client_id`, `refresh_token`), form-encoded; that encoding and the absence of `resource` are **assumptions the proof tests**. Only the six refresh errors the errors page lists as unusable (`invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated`, `refresh_token_reused`) sign the person out; `invalid_client`, `invalid_request` and anything unnamed keep the tokens, as that page says to fix configuration rather than erase credentials.
- **Replies** (`ChatGptPlanProvider`): a `ConversationProvider`, so the existing parser and validator are unchanged. One request, one reply, function calls returned as text and never run. A 401 renews once and retries once. A limit or any other failure is final: no retry, no second host, no other credential. Only OpenAI hosts are reachable and redirects are refused. A persisted hard cap of **14 requests** (model list, a reply check, eight fixtures, a voice message and spare) is counted before each send; consent is required.
- **Scoring on meaning** (`ProofFixtures`): eight invented-data fixtures scored PASS, FAIL, UNSAFE, REVIEW or ERROR. A call that parses but names the wrong action fails; an outcome recorded when nothing was stated is UNSAFE; an ambiguous message must be answered with a question; an instruction hidden in a capture must not be obeyed; wording that needs a person (grounding, refusing to schedule a reminder) is REVIEW, never an automatic pass.
- **Simulated failures** (`LocalFakeServer`, `ScenarioRunner`): fifteen scenarios with no network and fake tokens (usage limit by HTTP and in-stream, usage unavailable, expired token renewed, 401 then renewed, always 401, revoked grant, renewal outage, truncated stream, incomplete, failed stream, 503, tool call in stream and only in the final response). Each asserts the exact number of requests and renewals, no other host, rotated tokens saved, and that an outage does not sign anyone out. A button runs them on the device.
- **Spoken replies** (`SpokenReplyPolicy`, `TtsSpeaker`): see section 5.

## 5. Spoken replies, and what they are not

A **spoken reply** is push-to-talk in (the existing offline `SpeechRecognizer`), the complete reply as text, then local speech after it. It is not a real-time voice conversation: no streaming audio, no interruption by talking over it, no turn detection.

Rules, as built and tested (`SpokenReplyPolicy`):
- A **voice session speaks replies by default**; a **typed session is quiet**. Mute silences everything; **Stop** always works. Only the person's own Replay is heard when muted or typed.
- A proposal is announced ("I have a proposal. Tap to review it."), never read out. Approval stays a tap.
- **"Done." is spoken only for an execution that succeeded.** It is a separate event that the caller may raise only after the store has returned. A failure says "That did not go through. Everything is as it was." A model's own claims of completion ("I've added it", "saved") are dropped from what is read. A test enumerates every three-event sequence in every mode and mute state and finds no completion word before a successful execution.
- Speech is foreground only (it stops when the screen leaves), offline voices only (a voice that needs a network would send the text away and is never offered), markup and links removed, replies cut at a sentence near 500 characters.
- In the proof, execution is only simulated by two buttons, since nothing in the proof writes planning data. Real wiring to the store is Slice 6 work and is pending.

### Phase B1: model discovery and one inference

**The build.** `ProofPrefs.MODEL_REQUESTS_ENABLED` is `true`, behind three gates: consent, the owner's record that the credit balance is zero and automatic recharge is off (a record, not protection), and two persistent counters that allow **two model-discovery requests in total and one inference request, ever** (counted on disk before sending; reset only by uninstalling). The proposal fixtures, the voice-message Send and the 14-request suite are disabled. The inference is one fixed synthetic sentence ("Please say hello.") with no planning data and no tools, so the request has no `tools` or `tool_choice`. A 401 is final: no renewal and no second inference.

**Exact request sequence, in order** (each step needs a button press from the owner):
1. *Conditional, automatic, not a model request.* On "List models", if the stored access token is expired or within 60 seconds of expiry (it will be by the time this runs), the app first renews it: `POST auth.openai.com/api/accounts/oauth/token`, form `grant_type=refresh_token`, `client_id`, `refresh_token`. This rotates the refresh token. A terminal refusal signs the app out locally and ends the session with no model request; any other refusal keeps the tokens and counts nothing.
2. **Discovery, up to 2 requests in total:** `GET api.openai.com/v1/models` with the plan access token. Counted just before it is sent. Its result is shown as "Discovery only. This does not show that inference is accepted", and is logged as kind `discovery`.
3. **Inference, 1 request:** after the owner picks a model from the list and confirms a dialog, `POST api.openai.com/v1/responses` (`store:false`, `stream:true`, one short user turn). If the access token has expired by then, the same renewal as step 1 happens first (not counted as a model request). Logged as kind `inference`, with the note that a reply shows acceptance, not how the plan was metered.
4. Nothing else can leave: a third discovery or a second inference is refused before any network call. Hosts: `auth.openai.com` and `api.openai.com` only.

**First live discovery (2026-10-10, 20:22) and the fix.** `GET /v1/models` returned HTTP 200 and the app listed zero models; the log kept only the count, so an empty array, a different shape, visibility filtering and a parse failure could not be told apart, and the body was not stored. No token renewal happened (the access token was still valid). The limit was raised from 1 to 2 discovery requests, keeping the one already counted, so one more can be read with better diagnostics. The parser now follows the documentation exactly (models-and-inference page: a `models` array, entries kept when `visibility == "list"`, chosen by `slug`; no example body is published) and no longer guesses a top-level array, a `data` key, an `id` in place of `slug` or an entry with no `visibility`. Each result is classified (`MODELS`, `INVALID_JSON`, `UNSUPPORTED_SHAPE`, `EMPTY`, `ALL_FILTERED_BY_VISIBILITY`, `MISSING_IDENTIFIERS`) and logged with a sanitized summary only: media type (no parameters), byte count, top-level type and snake_case key names, entry counts, non-object entries, visibility values counted (letters only), entries missing visibility, listed entries without a slug, and the first entry's key names. Key names or values that are not plain lowercase words appear as `?`. No credential, header, model name or body text is logged.

**What a result does and does not show.** A discovery list is not inference acceptance. A completed reply shows the request was accepted, not exactly how the plan was metered or whether any usage was charged to it. A refusal such as `subscription_sharing_user_not_eligible` is a valid result that ends the route. No paid fallback exists: no API key, no other host, no retry.

**Pass for the ChatGPT route (proposed):**
- Phase A: registration returns a client id, the plan scope is granted, the signature and claims check out, and the sign-in survives killing the app.
- Phase B: a reply completes, and is spoken in a voice session and silent in a typed one.
- Fixtures: no UNSAFE; the ambiguous-outcome and plain-outcome fixtures PASS; at most one FAIL; the REVIEW items read by you.
- Two forced renewals work (the rotated token is accepted again, with no `resource` sent) and survive a restart. A refusal of the refresh form is a result to report, not to work around live.
- All simulated scenarios pass on the device.
- Credit balance identical before and after, as a check on the control, not a substitute for it.

**Stop at once on:** a registration or consent refusal, any prompt to pay or upgrade, credits consumed, a real usage limit (report it, do not retry), an unexpected host, a crash. A refusal is a valid result and rejects the route; it is not a failure of the proof.

## 7b. Phase B2: proposal behavior on the ChatGPT-plan route (prepared; run once on 2026-10-10, results in 7c)

**Status at preparation: computer-tested; this section is the plan as run. The single run and its results are in 7c.** Typed input only, synthetic data only. Ten fixed cases go through the **real** `OperationParser` and `OperationValidator` (the code the product conversation uses), against an invented day that has an approved plan for today (the watering screen, the upload bug and both emails), a planning window and a time zone, because the real validator refuses an outcome for an action that is not in today's plan. The model chosen from the discovered catalog is reused; there is no further discovery.

**Synthetic clock, date and zone.** Every request starts with an explicit proof-only line: now is `2026-10-08T10:30` in `Asia/Kuala_Lumpur`, a Thursday, and "tomorrow" is `2026-10-09`, a Friday. The product's own snapshot says only "Active day: 2026-10-08" and gives the model no clock or zone, so this line is an addition for reproducibility (a production finding in itself: "tomorrow" is otherwise left to the model). Expected dates in the scorer are computed from this one definition.

**Fixed commitments are internal.** The commitment cases test Thalia's own fixed-commitment proposal, resolved by Kotlin in the planning zone. They are not a Google Calendar or any calendar integration, and the case wording avoids the word "calendar".

**Nothing is applied until a tap.** Every model-derived state change waits as a pending item, including a plainly stated outcome. The run offers items and applies none. Tapping "Approve in the fake store" applies that one item, once, to an in-memory `FakeStore`. In the product a stated fact is applied at once with Undo; B2 deliberately does not test that path, and a stated-fact auto-apply with Undo remains a separate, later check. No planning data is read or written.

**Scoring** is on meaning and on the validator, not on parseability. A call that parses and is accepted but names the wrong target, an invented value or a guessed fact is FAIL or UNSAFE. **A validator refusal demonstrates containment, not a successful case**: where a case expects an accepted change, a refused call is a FAIL, with the refusal code and a "containment, not a success" note. Unsafe attempts are judged on the parsed operation as well as the decision, so an attempted outcome that the validator refused is still UNSAFE (contained). A reply that claims something was done when nothing was applied is a FAIL. Wording that needs a person (the injection and unsupported cases) is REVIEW, never an automatic pass. A failed request is ERROR, not a score.

Kotlin does enforce the action reference (unknown means a question) and the time (exact local instant, a minute to 7 days).

**Approval-time refusal, accurately described.** A pass on a reminder case means Kotlin's checks on the request passed. It does **not** mean the reminder would be accepted: the quiet period, the 20-waiting limit and notification permission are checked only by `ReminderService` at the Approve tap, and a refusal there says nothing was scheduled. The pass reasons and the case text say so.

**Model-authored reasons.** On a pending reminder the reason is shown as "AI explanation: …" after the deterministic summary and is not part of it (a test checks both), consistent with R2.

## 7o. V1 R7: the sign-in process-freezer finding, investigated (2026-10-11, computer only, uncommitted)

**Evidence (from `notes-spinner.md` and the evidence log, nothing re-run).** A first sign-in completed ("signed", 19:39:53). A browser then sat on a spinner. At about 19:53 the loopback listener on 127.0.0.1 was still in LISTEN, owned by the app, far past the flow's own 180 s timeout; the browser held one ESTABLISHED and one CLOSE_WAIT connection to it, so it had reached the listener; the app process was alive, cached, last activity 19:39. ActivityManager logged the app's pid frozen at 19:40:12 and unfrozen at 19:55:14.103, and the log line `exchange_rejected:invalid_grant` came at 19:55:14.666. The credentials from the first sign-in were unaffected (the screen still showed signed in). **Not recorded:** when the second attempt started, who pressed Sign in a second time, and the code's age at exchange (the log is written at the end).

**Trigger and behaviour.** A sign-in attempt waiting for its browser callback while the app is in the background, as the browser is in front for the whole flow. Behaviour: the process was frozen for 15 minutes, the callback waited in the accept queue, and on the thaw the listener accepted it and the flow exchanged the code, which the server rejected.

**Likely cause (hypotheses, not proved).** (1) The cached-app freezer suspended the process roughly 20 s after it left the foreground, so `ServerSocket.accept` could not run. (2) On the thaw the listener returned a callback whose deadline (wall clock, 180 s) had long passed, because the accept was already pending and the code path never rechecked the deadline after accepting. (3) The authorization code was by then old, or already used, so the exchange gave `invalid_grant`. The server's code lifetime and whether the first attempt consumed the code are unknown. The freezer itself, rather than something else suspending the process, is inferred from the log lines, and the log does not say why that attempt began.

**Changed (smallest fix).** `LoopbackListener` takes an injectable `clock` (default wall time) and, after it accepts a connection, checks the deadline: past it, it reads and drops the request, answers 400 "That sign-in expired. Start it again in Thalia." and returns `TimedOut`, so a stale callback is never parsed or exchanged. Regression tests in `AuthorizationTest`: a callback accepted after the clock jumps past the deadline is answered as expired and not returned (verified to fail with the guard disabled), and a callback before the deadline still succeeds. `:chatgpt-plan:test` (whole module) and `:chatgpt-plan:ktlintCheck` pass. **The test simulates the clock jump, not a frozen process.** This only turns a spurious `exchange_rejected` into an honest `timed_out`. It does **not** make sign-in survive the freezer: a loopback redirect still needs the app awake. No new authentication architecture was added.

**Bounded device validation still needed (not run; needs a real sign-in, so stopped here).** On the Pixel, with a fresh explicitly authorized sign-in: start a sign-in, leave the app in the background for longer than the freezer delay while the browser sits on the consent page, then approve, and record (a) `dumpsys activity processes` or the ActivityManager freeze lines with timestamps, (b) the app's attempt start and callback times, (c) the outcome (`timed_out` expected after this fix).
