# ADR 0013: Grounded text AI preparation (Slice 4A)

Date: 2026-10-08
Status: **Accepted 2026-10-08 as local preparation**, on computer tests and two isolated Pixel passes with a fake transport. **Live-model validation is pending:** no request to Google has been made, no billing is activated, no key has been entered and no build outside debug has `INTERNET`. Branch `v1/slice2-day-loop`, after `d4463a2`.
Amends: [ADR 0008](0008-m3a-manual-gemini-live-spike.md) decision 4 (the device-held key, text only), [ADR 0003](0003-optional-ai-provider-policy.md) decision 3 (the monthly figure, text only). Completes [ADR 0010](0010-text-conversation-operation-boundary.md)'s "consent, key and cost" and [ADR 0012](0012-capture-and-inbox.md)'s "gates must exist before a live provider".

## What this adds

Everything between "the person presses Send" and "a request leaves the phone", so that a live model can be wired later without any new decision about safety: consent, a device-held key, a persistent monthly budget, one gated door to the network, bounded context, private Inbox captures, and opening and closing entry points. It adds no voice, no call integration and no schema change (planning stays at schema 5). It wires **no live transport**: `ThaliaApplication` builds the gated provider with a null transport, and the manifest still requests `INTERNET` only in the debug build type, so in every build a Send is answered "unavailable" and sends nothing.

The transport and the typed operation boundary of ADR 0010 are unchanged: one `generateContent` POST on the OkHttp already in `:voice-gemini`, function calls returned as text, and Kotlin validating every call.

## Decisions

### 1. A device-held key, on this installation only (amends ADR 0008 decision 4)

The captain approved a standard API key held on the phone for the text conversation on this personal installation. The reasons ADR 0008 forbade it (a public app, shared builds) do not apply to one person's own phone, and the alternatives (a backend for ephemeral tokens, Firebase AI Logic with App Check) were weighed in ADR 0010 and cost more than they protect here. The prohibition stands for the Live API, voice, and any build another person installs.

Conditions: entered at runtime in a masked field; encrypted with an AES-256-GCM key generated in and never exported from the Android Keystore (alias `thalia-ai-gemini-text-key`, its own associated data, so a file sealed for the M3A spike does not open as this key); stored in the app's private folder, backup off; never shown again, never logged, never in a URL (the key goes in the `x-goog-api-key` header), never in `BuildConfig` or the repository, never in a planning export (it lives outside the planning files, and a test scans every other file the app wrote for it). **Clear key** deletes the file and the Keystore key. The cipher and store moved from `src/debug` to `src/main` (`com.thalia.app.secret`) with the Keystore alias and data as parameters; the M3A spike uses them with its old defaults. A key in a release build is harmless without `INTERNET`.

The owner should still create the key in its own Google Cloud project, restricted to the Generative Language API, with billing enabled, and rotate it if the phone is lost. Thalia cannot check any of that.

### 2. Consent and AI off

AI begins off. One screen (**AI settings**, reachable from the planning and conversation screens) holds the consent wording, a turn-on button, a turn-off button, the key and the budget. The wording names Google and the model, lists exactly what a Send carries, says Inbox captures are excluded except those chosen, says the conversation is not stored, says what Google's terms (read 2026-10-06) say about paid and Free tiers and that Thalia cannot tell which tier a key is on, and says the budget is an estimate. It is versioned (`ai-text-paid-2026-10-08`): changing a word withdraws every earlier consent. With AI off, no key or no budget, a Send is answered locally with the reason and "planning, outcomes and the Inbox work as usual"; nothing else in the app calls a provider (a test counts requests). This is ADR 0003's local-first rule: delete the AI and Thalia is still a complete v1.

### 3. One gated door, in this order (`GatedConversationProvider`)

1. A transport exists; consent to the current wording is on; a key is saved.
2. The request is within 48,000 UTF-8 bytes (instruction, snapshot, turns and tool declarations), and the person's message within 2,000 characters (checked earlier, in the session). Over the limit, nothing is sent and the reason is shown.
3. No other request is in flight (a second is refused as busy).
4. Its worst-case cost fits in the month's budget, and the allowance is **on the disk** (`fsync`) before the request is sent.

Then exactly one transport call is made. The conversation never sends a function result back to the model, so there is one round per message by construction, and a test asserts one call per allowed request. Output is bounded at 4,096 tokens, thinking included (the provider counts both against `maxOutputTokens` and bills both as output).

### 4. The budget (`BudgetLedger`): USD 5 a month, an estimate

An append-only file of lines `R` (allowance held), `S` (cost settled), `X` (allowance returned), `B` (budget set), forced to the disk before use. The month is the calendar month in UTC (Thalia's accounting month, not Google's billing cycle).

- **Reserve.** The worst case is the UTF-8 byte count of everything sent as an input-token ceiling (a token is never shorter than a byte, so it cannot be low), plus every allowed output token, at the **highest price in force within a day of the request** (Google does not say whose midnight its price dates use). A request that would pass the budget is refused and writes nothing. Exactly filling the budget is allowed.
- **Reconcile known usage.** A reply, or a refused reply that carries usage, settles at the reported cost: prompt tokens plus the larger of (candidates + thinking) and (the service's total less the prompt), so a field the service omits cannot lower the cost. A reply with no usage settles at the full allowance, never at zero.
- **Return only on evidence.** The allowance is returned in exactly two cases. (a) The transport made no request at all (a local failure before sending). (b) The service answered HTTP **400** or **500**, which Google's billing page documents as uncharged ("If your request fails with a 400 or 500 error, you won't be charged for the tokens used"; the same page adds that the request still counts against quota, and says nothing about 401, 403, 429, 503, 504 or timeouts; read 2026-10-08). Every other outcome without usage stays held: **401, 403 and 429 are undocumented, so they are uncertain, not released**, along with 502/503/504, timeouts and an unreadable 200. A refused or cut-off reply that reports usage settles at that usage. A consequence to know: a wrong key (401/403) holds a worst-case allowance each time it is tried, so repeated attempts with a bad key can consume the month's budget without a single successful answer; the screen says the allowance is held, and held allowances lapse only when the month ends.
- **The policy per status, exactly** (transport `GeminiTextConversationProvider`, gate `GatedConversationProvider`; tested through both in `GatedGeminiChainTest`):

  | Outcome | Allowance | Basis |
  |---|---|---|
  | 200 with usage (reply, refused or cut off) | settled at the reported cost | Google's `usageMetadata` |
  | 200 without usage | settled at the full worst case | processed, cost unknown |
  | 200 unparseable | held | processed, cost unknown |
  | 400 | released | billing page: "won't be charged" |
  | 500 | released | billing page: "won't be charged" |
  | 401, 403, 429 | **held** | not documented; the billing page names only 400 and 500 |
  | 502, 503, 504, other 5xx, other codes | held | not documented |
  | Timeout, dropped connection, transport threw, screen left, process killed | held | the request may have been processed |
  | No request made (transport unavailable) | released | nothing was sent |

  A hold is retired only by a settlement, a documented release, or the month ending. 401, 403 and 429 are therefore resolved as *uncertain*, not unbilled; nothing in this slice verifies otherwise, and verifying it would need a live request.
- **Retain the uncertain.** A timeout, a dropped connection, a 502/503/504, an unreadable 200, a transport that threw, a screen left mid-request and a process killed all leave the full allowance counted. Restarting changes nothing; nothing in the app clears one; it lapses only when its month ends. A line the file cannot parse (a torn write) is charged USD 0.15 in every month rather than ignored.
- **The ceiling.** The initial validation cap is USD 5 a month and it is also the most the app accepts (`Usd.AI_BUDGET_CEILING_MICROS`). The owner set the product's whole recurring technology cost, AI and hosting together, at RM 40 to 50 a month on 2026-10-08; that supersedes the earlier V2 and V3 allowances. How the ceiling is shared between AI and hosting is undecided, so no figure above the validation cap exists in the app: the budget can be lowered, and raised back up to USD 5, through a confirmation screen that names the old and new amounts; a figure above USD 5 is refused with nothing written, and a hand-edited ledger line above it is read as USD 5. Going higher needs a recorded decision and a code change, not a settings confirmation. The screen warns at 70% and 90% and says plainly when the month is used up.
- **What it is not.** It is not Google's invoice and not a hard cap. Clearing the app's data resets it; a price the table does not know is not in it; billing data lags. The screen and the consent wording say so. The backstops are outside the app: Google AI Studio's project spend caps ("hard limits", per Google's billing page) and a budget alert, which the owner should set in the key's project before the first real request. Thalia cannot verify that they are set.

Typical numbers at today's price (USD 0.75 per million input tokens, USD 3.75 per million output): a worst-case allowance is about USD 0.05 (48 KB of input plus 4,096 output tokens), so about 100 requests can be reserved at once from USD 5, while a real exchange of about 4,000 tokens in and 500 out settles near USD 0.005.

### 5. Model and prices, verified 2026-10-08

`gemini-3.8-flash` is listed as Stable on Google's models page; the same id is the pricing page's entry, dated 2026-10-07: paid tier USD 0.75 input and USD 3.75 output (thinking included) per million tokens through 2026-12-31, and **USD 1.50 and USD 7.50 from 2027-01-01**. The change is in the table (`GeminiPrices.TEXT`) with its read date, and the worst-case rule above prices the days around it at the higher figure. Both pages were read through a summarising fetch and not saved, so the first real request should be preceded by reading them again. The configuration is deliberately small: one model id, one price table, one output limit, one budget. Google lists cheaper Flash-Lite models; none was evaluated, and ADR 0010's choice stands.

### 6. Context: grounded, bounded, Inbox private

- The snapshot is the existing one (direction, goals, projects, open actions, today's plan and outcomes, fixed commitments, focus, last closing note, re-entry line), bounded by 40 actions, 15 projects, 8 goals, 600 characters of direction, the last 10 turns and the 48,000-byte request limit. Omissions are counted in the text.
- **Inbox captures are excluded from every ordinary conversation.** The snapshot says "captures are private and are not shared in this conversation" and the model is told not to mention them. Only **Triage with Thalia** shares any: it now picks, by that press, the oldest open captures up to 5, passes their ids to the conversation, and only those that are still open are included. Each is flattened and cut at 400 characters, marked `CUT` with the number cut and an instruction not to guess the missing part. Before Send, the conversation screen lists exactly which captures a Send will share and which are cut. A capture filed during the conversation drops out of the next request.
- The model is told its limits in the instruction: ground every recommendation in the snapshot or say what is missing; it cannot open or close the working day, set a closing note, schedule a reminder or place a call; accept a correction plainly. Kotlin still enforces the rest (ADR 0010, 0012).

### 7. Opening and closing entry points

Two buttons on the planning screen, **Plan the day with Thalia** and **Close the day with Thalia**, open the conversation with a fixed message in the box. Nothing is sent until the person presses Send. They use only existing operations: the model may propose a day selection, a commitment, a focus capacity or an action, and record a stated outcome; each is previewed, approved or undoable exactly as before. **Neither opens or closes a working day**, and no conversation operation exists for that (a test asserts that calls named `close_working_day` and `end_day` are refused, write nothing, and leave the working day open). **Explicit requests are routed, not refused.** A message that is plainly and only a request to open or close the working day ("close my day", "open the working day", "please wrap up the day"; up to 8 words) is recognised locally, before any provider: the conversation shows a **Day screen** line, "Closing the working day is done on the day screen, where you confirm it yourself. Thalia cannot do it from a conversation, so nothing was changed and the working day is as it was," with an **Open the day screen** button that returns to the planning screen, where the working day is opened and closed with its own confirmations. This works with AI off, costs nothing and cannot claim completion. If a model instead calls a made-up function to open or close the day, the same line is shown once and the model's own words are dropped, since they may say it was done. "Help me start my day" and the two entry-point drafts are planning requests and go to the model. Before this change, a made-up call got only the generic "Not applied: close_working_day, ..." refusal, which was a dead end. The conversation screen also says on its face that opening and closing are done on the day screen and that only lines labelled Saved were saved. Whether the model's prose claims something it did not do cannot be checked in Kotlin; the labels and the instruction are the mitigation, and the real-model check below tests it.

## What leaves the phone, once a live transport exists

Per Send, to `generativelanguage.googleapis.com`, over TLS, with the key in a header: the fixed instruction, the snapshot above (including the titles and text you wrote in actions, projects, goals, direction, context fields, commitments and the last closing note), up to 10 recent conversation lines including your message, and the function declarations. Not sent: Inbox captures (except chosen in a triage, up to 5, first 400 characters each), stored ids (the model sees `a1`/`p2`/`i1` references only), the key, other apps' data, the call and check-in schedule, or any planning export. Google returns text, function calls and token counts; Thalia does not store the conversation.

## Live check outcome so far, 2026-10-08

Slice 4A's local preparation stands as accepted. Live behaviour validation is **pending and paused**: two free-tier attempts against `gemini-3.8-flash` with synthetic data produced one grounded reply (attempt 1, Send 1) and then server errors before any of the other behaviours could be assessed (attempt 1, Send 2: an unrecorded server-class status; attempt 2, Send 1: HTTP 503). The cause of the failures is not known and no claim is made about it. A dashboard request count of 2 after attempt 1 is not treated as proof of the number of network attempts. The attempts led to two changes in the transport: it keeps the HTTP status (status only) and it makes one network attempt per call, because OkHttp otherwise resends some statuses itself. Details, evidence and the open questions: [ai-live-check-slice4a.md](ai-live-check-slice4a.md). One bounded same-model attempt may be authorized later by the owner.

## Limitations

- No live transport is wired and no request has been made to Google. The Gemini adapter's request and reply shapes are tested only against local fakes and Google's REST reference.
- Unproven: that `gemini-3.8-flash` accepts the request exactly as built (in particular that no `thinkingConfig` is needed and that a 4,096-token limit leaves room for an answer after thinking); that usage metadata arrives as the code reads it; that a model reads a plain sentence as the right operation; that its prose does not overclaim; recommendation quality.
- The budget is an estimate with no authority over Google's billing. A price absent from the table, a usage field Google adds, or billing for a request Thalia counted as unbilled is invisible to it. 401, 403 and 429 are assumed unbilled without documentation.
- Uncertain allowances cannot be cleared by hand in this slice; they lapse with the month.
- Clearing app data resets the budget and the consent.
- The tier of the key (paid or Free) cannot be checked, and the consent text rests on Google's terms as read on 2026-10-06.
- The settings and conversation screens are functional and unstyled, and have not been run on the phone. No Compose UI test exists for them; their logic (text, warnings, parsing) is tested apart from the screen.
- The planning screen's Triage button now selects ids in the activity; that path (and the two entry points) was inspected and compiled, not tapped.
- The real debug app, its schema-3 data, its alarms and the Stage G candidate were not touched.
